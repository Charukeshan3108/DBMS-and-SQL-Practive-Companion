Relationship rules

  • Member → Loans

    One member can have many loans; each loan belongs to one member.

  • Book → Loans

    One book can appear in many loan records over time.

  • Author → Books

    One author can be linked to many books in this simplified model.

Schema starter

CREATE TABLE Members (
  member_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT UNIQUE
);

CREATE TABLE Loans (
  loan_id INTEGER PRIMARY KEY,
  member_id INTEGER REFERENCES Members(member_id),
  book_id INTEGER REFERENCES Books(book_id),
  loan_date DATE NOT NULL
);

THE FOUNDATIONS

Core database concepts

A concise study guide for third-semester CSE students.

◇

01 · DESIGN

ER modelling

Represent entities, attributes, and relationships before creating tables.

Remember

Choose stable primary keys and enforce relationships with foreign keys.

▤

02 · STRUCTURE

Normalisation

Organise relations to reduce redundancy and avoid modification anomalies.

Remember

1NF: atomic values. 2NF: no partial dependency. 3NF: no transitive dependency of non-key attributes.

⇄

03 · QUERY

Joins

Combine related rows from tables using a join condition.

Remember

INNER JOIN returns matching rows; LEFT JOIN preserves all rows from the left table.

⚡

04 · PERFORMANCE

Indexing

An index can speed up lookups, but consumes storage and can slow writes.

Remember

Use query plans and representative data; don't index every column automatically.

⟳

05 · RELIABILITY

Transactions

Group operations into a unit of work that can commit or roll back.

Remember

ACID: Atomicity, Consistency, Isolation, Durability. Exact behaviour depends on the database engine.

✳

06 · AI LITERACY

Verify AI output

AI explanations are drafts. Confirm syntax, results, and advice against documentation.

Remember

Never paste real student or patient data into public AI tools.
